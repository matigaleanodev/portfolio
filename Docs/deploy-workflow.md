# Portfolio Deploy Workflow

This document defines the deploy flow currently executed from the `portfolio` repository, including the final handoff to `portfolio-cloud` and the editorial artifact export used by the rest of the ecosystem.

The final cross-repository ownership is documented in [Docs/ecosystem-ownership.md](./ecosystem-ownership.md).

## Current Scope

The workflow also runs daily at 09:17 Argentina and manually on `main`, with serialized execution and future posts excluded at build time. Daily runs skip Angular/Firebase if the live publication state matches the commit and eligible posts; cloud recovery steps still run. Pushes/manual runs force deployment. See [scheduled publication](./scheduled-publication.md) for editorial rules, activation, and recovery.

The repository is responsible for:

- generating static editorial content from `content/`
- building the Angular application with prerendered blog routes
- deploying the static output to Firebase Hosting
- exporting a release manifest for `portfolio-cloud`
- exporting `.generated/chat/knowledge.json` as an editorial handoff artifact
- invoking `process-release` after a successful Firebase deploy
- invoking `publish-chat-knowledge` after `process-release`

This repository is not yet responsible for:

- SES notifications
- the internal orchestration logic of `process-release`
- subscriber persistence or blog mail delivery

Those pieces remain owned by `portfolio-cloud` and `portfolio-api`.

## Current Pipeline

The current GitHub Actions flow is:

1. `npm ci` and `npm run build:content`
2. confirm the revision is the head of `main` and decide whether Firebase needs a deployment
3. `npm run build:app` (Angular build and `404.html`) and publication marker
4. `npm run build:release-manifest` and `npm run build:chat-knowledge-payload`
5. install the Firebase CLI pinned in `tools/firebase-cli` and deploy `dist/portfolio/browser`
6. invoke `portfolio-cloud-<stage>-process-release` with `.generated/release-manifest.json`
7. invoke `portfolio-cloud-<stage>-publish-chat-knowledge` with `.generated/chat/knowledge-payload.json`
8. upload the release manifest, chat knowledge artifact, invoke payload, and Lambda responses as workflow artifacts

The `firebase-tools` version is exact and resolved by the lockfile in `tools/firebase-cli`, kept apart from the application one. Update it by changing the version and lockfile in a PR; CI uses it as the Hosting emulator.

## Firebase Hosting Strategy

Firebase Hosting serves `dist/portfolio/browser`.

Key rules:

- prerendered HTML stays cache-sensitive
- non-hashed XML assets (`rss.xml`, `sitemap.xml`, `sitemap-blog.xml`) stay cache-sensitive
- generated JSON indexes stay short-lived
- hashed JS/CSS and static images remain immutable
- there is no global rewrite: every publishable route has its prerendered HTML and anything else returns HTTP 404 with `404.html` (`noindex`, no canonical). A new route must be added to `app.routes.server.ts` or Hosting answers it as missing
- `404.html` comes from the `404` route, prerendered and moved by `scripts/build-not-found.mjs`
- the only rewrite serves the unsubscribe confirmation for the matrix-parameter link (`/blog/unsubscribe;email=`)
- `index.html` declares the RSS feed with `rel="alternate"` and `robots.txt` declares `sitemap.xml` and `sitemap-blog.xml`

This keeps static blog pages deployable without reintroducing runtime content fetches from the backend.

## Editorial Knowledge Handoff

`build:content` also generates `.generated/chat/knowledge.json`.

This file remains a frontend-owned build artifact, but the direct filesystem sync to EC2 is no longer the target integration.

The agreed direction is:

- `portfolio` exports the artifact
- `portfolio-cloud` will manage the canonical copy in R2 through dedicated Lambdas
- `portfolio-api` will resolve that knowledge dynamically from the cloud-backed source, with local fallback or cache as needed

The deploy pipeline now also builds `.generated/chat/knowledge-payload.json` with:

- `artifact`: the raw editorial artifact generated by `portfolio`
- `release`: `generatedAt` and `siteUrl` copied from `.generated/release-manifest.json`
- `source`: repository and artifact path metadata for the cloud envelope

`portfolio` still does not build the final cloud envelope. That remains owned by `publish-chat-knowledge` inside `portfolio-cloud`.

## Release Manifest

The pipeline now generates `.generated/release-manifest.json`.

Its purpose is to give `portfolio-cloud` a stable handoff artifact with:

- git SHA and ref
- deploy target metadata
- slug, title, date, canonical path and excerpt (optional for the consumer) of each post
- project slugs
- SEO file paths

The deploy workflow now invokes `process-release` directly after Firebase Hosting succeeds.

Current contract:

- source artifact: `.generated/release-manifest.json`
- trigger point: successful deploy on `main`
- invocation mode: private `aws lambda invoke`
- target function: `portfolio-cloud-<stage>-process-release`
- consumer responsibility: decide whether there are new posts and execute post-publication automations

This keeps the `portfolio` repository focused on static build and deploy, while `portfolio-cloud` owns event-driven execution.

## Required GitHub Configuration

- `AWS_ROLE_TO_ASSUME`
- `AWS_REGION`
- `PORTFOLIO_CLOUD_PROCESS_RELEASE_FUNCTION_NAME` optional, defaults to `portfolio-cloud-prod-process-release`

## Versioned Releases

The package version (`package.json` and lockfile) and the notes in both languages (`Docs/releases/vX.Y.Z.es.md` and `Docs/releases/vX.Y.Z.md`) are prepared on a work branch with a PR into `dev`. Promotion is a pull request from `dev` into `main` (see [pull request integration](#pull-request-integration)).

When a pull request from this repository that changes the version is merged into `main`, `release.yml` creates the annotated tag `vX.Y.Z` on the merge commit and publishes the GitHub release `Portfolio vX.Y.Z`, with the Spanish notes and marked as latest. Nothing is published if the version goes down, or if it does not change and already has a tag at another revision. A version without a tag goes out with the next pull request merged into `main`; if publication fails after the tag is created, running that run again completes it. It fails without publishing if those notes are missing, if a `release/` branch does not match the version, or if the tag already exists at another revision.

The release is published on merge, without waiting for the deployment: production validation comes afterwards and a problem is fixed with a revert or a new version. The Firebase deployment and the `dev` sync run independently on the push to `main`.

## Pre-deployment contract and browser checks

The chat knowledge generator resolves project links against the public site origin. The payload builder rejects relative, non-HTTP(S), or credential-bearing links before the Firebase deployment step, preventing publication of an artifact rejected by the Cloud/API consumers.

## Continuous Validation

`ci.yml` runs on pull requests and pushes to `dev` and `main`, without secrets and apart from deployment. It uses Node 22, lockfile dependencies, the npm cache, and cancels superseded runs of the same pull request; each push is validated separately.

| Job       | Contents                                                                                               |
| --------- | ------------------------------------------------------------------------------------------------------ |
| `quality` | formatting, lint, TypeScript and unit tests                                                            |
| `build`   | production build, release manifest and knowledge payload                                               |
| `browser` | against that same build: prerendered HTML without JavaScript, Hosting contract and Playwright Chromium |
| `verify`  | requires the three previous jobs to succeed                                                            |

The `dev` and `main` rules require `verify` and the `CodeRabbit` check; they are configured in GitHub, not in the repository. See [pull request integration](#pull-request-integration).

The build and unit tests preload `e2e/support/offline-build.cjs`, which rejects non-local connections and answers the Google Fonts stylesheet with `e2e/fixtures/google-fonts.css`; update that copy when the fonts change. Browser tests use the Firebase Hosting emulator with the `demo-portfolio` project, intercept the API and resolve no external names.

`.prettierignore` lists the files that predate the format check; remove each one from the list as it gets formatted.

Local reproduction:

```bash
npm ci
npm ci --prefix tools/firebase-cli --ignore-scripts
npm run build:content
npm run format:check && npm run lint && npm run typecheck && npm test -- --watch=false
npm run build
npx playwright install --with-deps chromium
PORTFOLIO_E2E_BUILD=true npm run test:e2e
```

`npm run test:e2e` without the variable starts the development server and skips the HTML and Hosting tests.

## Pull Request Integration

To merge a pull request: review it, check that GitHub enables **Merge pull request** and press it. No commands or workflow runs are needed.

Rules for `dev` and `main`, with no bypass for anyone:

- Pull requests only: no direct pushes, force pushes or deletion.
- `verify` (GitHub Actions) and `CodeRabbit` passing on a branch that is up to date with the target.
- Review conversations resolved. No approval from another person is required.
- Single merge method: merge commit.

Auto-merge is GitHub's native feature and is optional: enable it on each pull request with **Enable auto-merge** and GitHub merges once every rule is met. Into `main` it is only enabled with the owner's explicit authorization; GitHub does not enforce that restriction. It merges whatever head exists at that point, including commits added after enabling it. The exception is the [synchronization](#synchronizing-main-into-dev) pull request into `dev`, where the workflow enables it.

Cases that need an extra action:

- Branch behind: **Update branch**. Auto-merge does not update the branch; if the target moves while it waits, the button has to be pressed.
- `CodeRabbit` check missing or cancelled: comment `@coderabbitai full review` on the pull request.

The `CodeRabbit` check means its review finished, not that it approved. It also passes when the review is skipped, paused or rate limited and, with the default configuration, when it fails. Findings opened as conversations block until resolved; those listed only in the review body do not block, and auto-merge does not wait for them to be read, including those on commits added after enabling it. To review them before merging, merge manually.

Merging into `main` deploys automatically: see [current pipeline](#current-pipeline).

### Synchronizing `main` into `dev`

After each push to `main`, `sync-dev.yml` opens a pull request from `fix/sync-main-<sha>` into `dev` if `dev` lacks that revision, enables native auto-merge with a merge commit, updates the branch if `dev` moves, and waits until it is merged. It needs no approval or manual action, and the `dev` rules apply without exceptions.

The run fails and reports the pull request in its summary if there are conflicts, `verify` or `CodeRabbit` fails, conversations remain unresolved, the pull request is closed, its state or conversations cannot be read, the branch cannot be compared or updated, auto-merge cannot be enabled, or it is not merged in time (80 reads 30 seconds apart, with a 50-minute limit for the job). If auto-merge was already enabled, GitHub merges once the cause is fixed; otherwise, running the workflow again resumes the same pull request.

It uses `DEV_SYNC_PAT`, with contents and pull request write access, to create the pull request, enable auto-merge and update the branch: with `GITHUB_TOKEN`, CI would wait for manual approval. State is read with `GITHUB_TOKEN`. If `main` carries `.github/workflows/` changes that `dev` lacks, the token also needs workflows write access. While `dev` lacks `main`, a pull request from `dev` into `main` is out of date and cannot be merged.

## Current Revision, Retries and Rollback

Only the head of `main` publishes. `scripts/current-revision.mjs` asks the GitHub API when deciding the deployment and again right before Firebase, `process-release` and `publish-chat-knowledge`. If the revision fell behind or GitHub cannot confirm it, the job fails without running that effect or the ones depending on it. The check is not atomic with the effect; publications are serialized, so the run for the newer revision executes afterwards.

To retry: use **Run workflow** on `main`, or re-run the run of the current head. An older run fails on purpose. If `main` moved during a run, the next one completes the pending work.

To roll back:

1. Revert the change on `main` through a PR. The revert is a new head and is published the normal way.
2. Do not revert `#email=` support in unsubscription (`src/index.html` and the unsubscribe page): notifications already sent use that link.
3. A rollback from the Firebase console is only an emergency measure for the site: it also restores the publication marker, and the scheduled run will deploy `main` again. Finish the revert before that run or disable the workflow meanwhile. It does not undo notifications or chat knowledge, and must not pick a version without `#email=` support.

## Production target verified on 2026-10-09

The public site uses only the `prod` stage. `dev` is reserved for testing. AWS and the three repositories use `us-east-1`; the browser console may open another region and must not be used as evidence of the deployment region. The frontend GitHub variables currently target `portfolio-api-cloud-test-process-release` and `portfolio-api-cloud-test-publish-chat-knowledge`, the physical names of the `portfolio-api-cloud` installation. The workflow fallbacks are still the `portfolio-cloud` names: removing the variables would send publication back to those functions.
