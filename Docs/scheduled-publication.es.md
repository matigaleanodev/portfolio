# Publicación programada del blog

Preparar los posts en `content/posts/<slug>/index.md` con `date: 2026-10-15` y `draft: false` cuando estén listos. Mantener `draft: true` durante la revisión: los borradores nunca se publican automáticamente. `date` es un día calendario en `America/Argentina/Buenos_Aires`, no una hora por post. Los posts futuros se excluyen hasta la medianoche local; un push/deploy manual de ese día puede publicar antes de la ejecución diaria.

El build de contenido usa un único corte por ejecución y excluye posts futuros/borradores del índice, JSON de detalle, RSS, sitemap, conocimiento del chat y manifiesto de release. El prerender consume el índice filtrado. Los JSON de detalle generados se limpian antes de regenerar para retirar archivos viejos al reprogramar. `/blog/:slug` sigue siendo una ruta genérica de Angular; un post no publicado no tiene página/contenido generado y la navegación directa muestra el estado de error/no disponible existente. No hace falta controlar el reloj del navegador.

## Despliegue y recuperación

`deploy-firebase.yml` corre diariamente a las 12:17 UTC (09:17 Argentina), con pushes a `main` o desde Run workflow sobre `main`. La ejecución diaria genera contenido y compara el hash del índice de posts y el commit fuente contra `/publication-state.json` del sitio público. Si ambos coinciden, omite la compilación Angular y el deploy a Firebase. Un cambio en los posts habilitados o en el commit dispara el deploy completo; comparar el commit también recupera deploys fallidos de código que no cambiaron los metadatos de posts. Los pushes y ejecuciones manuales siempre despliegan. Si la marca no existe, es inválida o no se puede consultar, se despliega en lugar de omitir una publicación sin evidencia. El primer deploy instala la marca, servida sin caché; no hace falta otro secreto ni servicio de almacenamiento.

Los pasos cloud siguen corriendo después de desplegar correctamente o verificar que ese mismo contenido/código está publicado, para reintentar un fallo de mail/conocimiento sin volver a desplegar Firebase. Las ejecuciones de deploy se serializan. GitHub puede demorar los schedules: se publica al completar Firebase, no en un minuto exacto. El cron se activa al integrar el workflow a la rama predeterminada `main`. Se reutilizan secretos y variables existentes de Firebase/AWS.

Orden: build → Firebase → `process-release` (OG y mail) → `publish-chat-knowledge`. Se controlan metadatos de invocación y estado de respuesta de las Lambdas; los fallos parciales hacen fallar el workflow. Tras resolver el problema, reejecutar sobre `main`. El corte incluye posts vencidos; `notifiedAt` persistido omite notificaciones completadas. Se conservan las limitaciones del envío actual: una entrega parcial a destinatarios o un fallo antes de guardar estado puede duplicar mails al reintentar; este cambio no implementa deduplicación por destinatario.

Cloud rechaza fechas futuras/inválidas antes de procesar un release, enviar notificaciones con fecha o publicar conocimiento del chat. La API también filtra posts futuros/inválidos del contexto editorial, incluido el fallback local. La publicación normal depende del manifiesto del frontend desplegado, no del reloj de la API.

Desplegar primero las protecciones de cloud y API, y después integrar/desplegar el workflow del front y el contenido. Validar URL pública del post, índice, RSS y resultados cloud después de la primera ejecución programada. Las pruebas locales no despliegan ni envían mails.

Poner `draft: true` o una `date` futura retira un post existente en el próximo deploy, pero no revierte mails ni vistas. Cambiar la fecha de un slug ya notificado no vuelve a anunciarlo. Los posts nuevos con fecha pasada/actual se publican con el deploy normal de `main`. El historial del repositorio y los assets de imágenes no son un almacén privado de borradores; el texto futuro se excluye de los artifacts del sitio, no se oculta a quien lea el repositorio fuente.
